# Plan: a complete port of Magit 4.4.0

e8-magit is a subset of Magit: the status buffer, staging, committing, branching, pushing, pulling, rebasing, stashing, a plain log and plain diffs, with every menu laid out as Magit's. This plan takes it to the whole of Magit 4.4.0, the E8 way: each step ports named files of Magit's Lisp closely, records what Magit shows in Emacs 30 and tests the port against the recording, and lands as a pull request of its own. The table is the state; a session resumes from it.

Sizes are the Lisp ported, from `wc -l` of Magit 4.4.0's `lisp/`; the port is about a third as long in TypeScript. Magit's `lisp/` is 35,131 lines and transient.el 5,852; the port, with e8-magit-section and e8-with-editor, is 2,854.

## How a step is done

- **One branch and one pull request per step**, from `main`, merged before the next step starts; a step that grows past a session is split where its tests pass, and the rest becomes a row of its own in the table. The pull request updates this table and the README's "What works" and "What is missing".
- **Read the Lisp first, port it closely**: its names (kebab-case as camelCase in TypeScript, `-p` as `P`), its messages, its order, its faces and options, as the E8 docs say ([docs/working.md](https://github.com/e8-editor/e8/blob/main/docs/working.md), [ADR 0013](https://github.com/e8-editor/e8/blob/main/docs/adr/0013-following-org-closely.md)). The recordings come from Mark's Emacs's Magit, built in `~/.emacs.d/elpaca/builds/magit` from `~/.emacs.d/elpaca/repos/magit` (4.4.0 and 43 commits, `v4.4.0-43-g9bd644a`): read that source, not the tag's, so the port and the recordings agree.
- **Record, then match.** Before porting a buffer or a menu, add its case to `test/record.el` and run `emacs -Q --batch -l test/record.el`, which writes what Magit shows; the test compares E8's buffer with it key by key, as `magit-the-status-buffer-shows-what-magit-shows` does. A command that changes the repository is tested by what `git` shows afterwards. Nothing is guessed: where the Lisp is unclear, batch Emacs answers, `emacs -Q --batch -l test/record.el` or an `--eval`.
- **`make test` and `make types` pass before the pull request**, on the E8 on the PATH (a release, or a build of `main`), and `tsc -p .` is clean. A step that needs something E8 lacks says so in its row and gets that done first in E8, as a pull request there, since a package cannot work around the core.
- **What E8 does not match is written down** in the README's "What is missing", with why, rather than left silent.

## The steps

### 0. The oracle records buffers

`test/record.el` records the menus of the test repository. Extend it to record buffers too, as text without properties plus each line's faces, into `test/oracle/NAME.txt`, for a set of fixture repositories made the same way in Lisp and in `test/magit-tests.ts`: the present one (a commit, a change unstaged, one staged, an untracked file); one with an upstream, stashes, commits unpushed and unpulled, and a tag; one in the middle of a rebase stopped on a conflict; one in a merge with a conflict; one with a rename, a binary file and a file deleted. Record for each the status buffer, its sections cycled with `TAB` and `1` to `4`, the log of the current branch, the diff of the worktree and of a commit, the revision buffer of a commit and of a stash, and every menu and submenu the dispatch and file-dispatch menus open. Add a helper to the tests that makes the fixture, opens the buffer and compares with the recording; convert the existing comparisons to it. Done when every buffer the port shows today is compared with a recording and the recordings are regenerated by one command.

The biggest step: ediff.el and its files are about 10,000 lines; take `ediff-buffers` and `ediff-files` first, the merge second.

### 16. The parity audit

Record from Emacs the lists Magit defines: every interactive `magit-*` and `git-*` command, every `magit-*` option with its default, every face, and each mode map's keys. Tests compare them with the port's, allowing a listed exception each with its reason in the README. Go through the differences; port or list each. Then rewrite the README: "What works" is everything, "What is missing" is the listed exceptions, and the version becomes 1.0.0.
